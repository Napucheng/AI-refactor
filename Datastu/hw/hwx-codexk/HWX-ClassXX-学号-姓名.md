# Homework X Report

## 1. 作业目标与问题抽象

这道题的本质不是做一个“看起来很聪明”的调度器，而是先做一个**严格符合物理约束**、可以被评测程序逐单重算验证的调度器。

我采用了一个很朴素的建模方式：

- 每个快递员只保留 3 个状态：当前位置 `(x, y)`、下一次空闲时间 `available_time`、编号 `courier_id`。
- 每笔订单只做一件事：枚举所有快递员，计算其最早可能送达时间。
- 只有当 `delivery_time <= order_time + 30` 时才分配，否则直接不分配。

这样做的原因很直接：题目的评分前提是**先通过合法性验证**。如果输出格式、时间线或送达时间公式有问题，再复杂的优化都没有意义。

## 2. 算法设计思路 (Implementation Approach)

### 2.1 核心想法

整体策略是顺序处理订单，前 `m` 单视为预订单，之后视为即时订单。对每笔订单：

1. 枚举全部快递员。
2. 根据订单类型，用题目公式计算该快递员的最早送达时间。
3. 过滤掉超时候选。
4. 在合法候选里选择最早送达的快递员。
5. 若没有合法候选，则输出未分配结果。

这是一种事件驱动的贪心调度。它不追求全局最优，但有三个明显优点：

- 规则简单，容易验证。
- 每次决策只依赖当前状态，不会引入回溯和复杂搜索。
- 时间复杂度稳定，足以覆盖题目上限。

### 2.2 两类订单的送达时间公式

#### 预订单 (pre-order)

预订单允许快递员在自己空闲后提前前往取货点，因此：

```text
arrive_at_pickup = available_time + dist(courier_pos, pickup) / speed
delivery_time = max(arrive_at_pickup, order_time) + dist(pickup, delivery) / speed
```

如果快递员提前到达取货点，则必须等到 `order_time` 才能取货。

#### 即时订单 (instant order)

即时订单在到达前不可见，因此最早出发时间为：

```text
depart_time = max(available_time, order_time)
delivery_time = depart_time
              + dist(courier_pos, pickup) / speed
              + dist(pickup, delivery) / speed
```

### 2.3 候选选择规则

合法候选之间按以下顺序选择：

1. `delivery_time` 更早者优先。
2. 若送达时间相同，则当前 `available_time` 更早者优先。
3. 若仍相同，则 `courier_id` 更小者优先。

这样可以让 tie-break 规则保持确定性，避免相同输入产生不稳定结果。

## 3. 数据结构与状态定义

程序只定义了两个核心数据类。

### `Order`

```python
@dataclass
class Order:
    id: int
    t: float
    sx: float
    sy: float
    ex: float
    ey: float
    is_preorder: bool
```

### `CourierState`

```python
@dataclass
class CourierState:
    courier_id: int
    x: float
    y: float
    available_time: float
```

这种设计是刻意压缩过的。题目真正需要的动态信息只有“人在哪、什么时候空闲”，其余状态都可以由当前订单和题目规则推导出来，没有必要额外堆很多字段。

## 4. 调度流程与关键实现

主程序流程如下：

1. 从 `stdin` 一次性读取全部输入。
2. 解析第一行得到 `L, W, n, m`，随后解析订单列表。
3. 初始化 `n` 个快递员，全部位于 `(0, 0)`，`available_time = 480.0`。
4. 按输入顺序处理订单：
   - 计算每个快递员的最早送达时间；
   - 选择最优合法候选；
   - 若成功分配，则更新快递员的送达位置和空闲时间；
   - 若不分配，则快递员状态完全不变。
5. 输出逐单结果，并在最后输出总完成数和总收入。

几个关键实现点：

- 距离统一使用曼哈顿距离。
- 速度固定为 `0.5 km/min`。
- 输出时间统一格式化为两位小数。
- 不分配时固定输出 `0 -1.00 0`。
- 总收入按 `total_completed * 10` 计算，输出为两位小数。

## 5. 时间复杂度与正确性说明

### 5.1 时间复杂度

设总订单数为 `T`，快递员数为 `n`。

- 每笔订单枚举全部快递员一次；
- 每次枚举只做常数次运算。

因此总时间复杂度为：

```text
O(T * n)
```

在题目上限下，`T <= 5000, n <= 100`，总共最多约 `5 * 10^5` 次候选评估，Python 可以轻松承受。

空间复杂度为：

```text
O(T + n)
```

其中 `T` 来自订单存储，`n` 来自快递员状态数组。

### 5.2 正确性说明

该实现满足评测要求的原因如下：

- 每个快递员只有一个 `available_time`，因此不会出现同一快递员并行配送两单。
- 成功分配后位置更新为送达点，下一单的出发位置与题意一致。
- 预订单与即时订单分别使用题面给出的不同公式。
- `success` 仅在 `delivery_time <= order_time + 30` 时输出 `1`，与题意完全一致。
- 未分配订单不会更新任何快递员状态，因此不会污染后续时间线。

## 6. 性能测试结果与分析

我使用了 4 组针对性测试和 1 组压力测试。

### 6.1 样例测试

输入：

```text
10.00 10.00 3 2
1 480.00 2.00 3.00 5.00 6.00
2 500.00 8.00 7.00 8.00 9.00
3 510.00 1.00 1.00 4.00 5.00
4 530.00 7.00 2.00 9.00 8.00
```

程序输出：

```text
1 1 502.00 1
2 2 514.00 1
3 3 528.00 1
4 1 558.00 1
4 40.00
```

这个输出与 PDF 中参考解不同，但符合题意。题目已经明确说明参考输出不是唯一答案，评测重点是物理可行性和逻辑一致性。

### 6.2 预订单等待测试

输入：

```text
10.00 10.00 1 1
1 500.00 1.00 1.00 2.00 1.00
```

输出：

```text
1 1 502.00 1
1 10.00
```

分析：

- 快递员 480 分钟上线，从原点到 `(1,1)` 需要 `4` 分钟；
- 484 分钟到达取货点，但订单时间是 500；
- 必须等待到 500 才能取货，再花 `2` 分钟送达；
- 因此正确送达时间为 `502.00`。

这组数据验证了“预订单允许提前前往，但不能提前取货”。

### 6.3 即时订单不能提前出发

输入：

```text
10.00 10.00 1 0
1 500.00 1.00 1.00 2.00 2.00
```

输出：

```text
1 1 508.00 1
1 10.00
```

分析：

- 即时订单在 500 分钟前不可见；
- 快递员不能像预订单那样提前去取货点等待；
- 因此只能在 500 分钟出发；
- `(0,0)->(1,1)` 需要 `4` 分钟，`(1,1)->(2,2)` 再需要 `4` 分钟；
- 最终送达时间是 `508.00`。

这组数据验证了即时订单和预订单的行为差异。

### 6.4 不分配不污染后续状态

输入：

```text
10.00 10.00 1 0
1 480.00 9.00 9.00 10.00 10.00
2 490.00 1.00 1.00 2.00 2.00
```

输出：

```text
1 0 -1.00 0
2 1 498.00 1
1 10.00
```

分析：

- 第 1 单距离过远，30 分钟内无法完成，因此不分配；
- 若程序错误地把失败单也写入快递员状态，第 2 单就会被拖慢甚至失败；
- 实际输出中第 2 单仍能按原点出发并成功，说明未分配订单没有污染后续状态。

### 6.5 压力测试

测试条件：

- `n = 100`
- `m = 1000`
- `total = 5000`
- 随机生成合法订单，保证输入规模达到题目上限

在当前环境中的一次运行结果：

```text
输出行数: 5001
最后一行: 1125 11250.00
运行时间: 0.5671 s
```

分析：

- 输出行数正确，说明每单都有结果且包含最终汇总行；
- 运行时间明显低于题目给出的 30 秒限制；
- `O(T * n)` 的实现对于本题规模是足够安全的。

## 7. 遇到的困难与解决方案

### 困难 1：预订单与即时订单的行为差异很容易写混

如果把两类订单统一成同一个出发公式，会直接导致送达时间错误。尤其是预订单可以提前到取货点等待，而即时订单不能提前得知订单。

解决方法：

- 单独写 `predict_delivery(order, courier)`；
- 在函数内部按 `is_preorder` 分支处理；
- 让题目中的两套公式在代码里直接一一对应。

### 困难 2：失败订单是否更新状态

直觉上有人会想“虽然失败了，也许快递员还是跑了这单”。但题目评分只要求输出一条合法调度时间线，而不是模拟“接单后送失败”的全部行为。如果错误更新状态，会让后续时间线混乱，反而更容易被判错。

解决方法：

- 默认策略是：无法在 30 分钟内成功送达时，直接不分配；
- 未分配订单输出 `0 -1.00 0`；
- 同时完全不修改任何快递员状态。

### 困难 3：如何在稳定性与得分之间取舍

更复杂的启发式调度可能在某些数据上拿到更多完成单，但也更容易引入边界 bug。

解决方法：

- 先选择最简单、最容易验证的贪心策略；
- 确保每条输出都能被题面公式独立解释；
- 优先拿稳定分，再考虑进一步优化。

## 8. 总结

这份实现的重点不是“聪明”，而是“干净、可验证、不会失手”。

我把问题压缩成了最小必要状态：订单描述 + 快递员位置与空闲时间。然后用题面公式逐单做最早送达推演，只在能成功时才分配。这种实现虽然不是全局最优，但它非常适合作为课程作业提交版本：结构清晰、合法性强、性能稳定、容易解释。
